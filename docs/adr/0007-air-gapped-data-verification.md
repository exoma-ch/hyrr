# ADR 0007 — The air-gapped install carries the signed upstream artefact

- **Status**: accepted
- **Date**: 2026-08-13
- **Implements**: closes #614, completes #594
- **Scope**: `core/src/data_fetch.rs`, `core/build.rs`, `hyrr.json`, the six
  workflows that sparse-check-out `nucl-parquet`
- **Supersedes**: the P1 design recorded on #594 (a self-signed manifest), which
  is unimplementable — see below

## Context

#613 (ADR 0006 lineage) authenticated the **network** fetch: a minisign
signature over the release tarball, verified against a key pinned in
`hyrr.json`. The **air-gapped** path was left accepting any file handed to it.

That asymmetry is worse than verifying neither. It advertises a guarantee that
does not hold precisely where users most depend on it: isolated control networks
are normal at accelerator and hospital sites, and for some users `--from` is the
*only* install path. Until this, the cheapest attack on a HYRR install was to
hand someone a USB stick.

Four independent reviews (air-gapped operations, supply-chain cryptography, Rust
implementation, adversarial) informed the decision; consolidated on #614.

## Decision

### 1. The originally-planned design is dropped

#594 P1 proposed that `export_offline_bundle()` write a `manifest.json` plus a
`.minisig`. **It cannot be built as specified.** `export_offline_bundle` runs on
an ordinary user's machine, and the data-signing key is held offline by the
nuclear-data team. A manifest signed by nobody, living inside the bundle it
describes, is rewritable by anyone who can rewrite the files — it reads as a
control while being none.

All four reviewers rejected it independently. The cryptographic review's phrase
is the one to remember: *"actively harmful — reads as a control, isn't one."*

Two neighbouring ideas were rejected for the same underlying reason:

- **A throwaway keypair generated by the exporter.** The signature would prove
  "a machine holding this key signed it", which is a tautology. Trust-on-first-use
  with extra steps.
- **Content-addressed reconstruction** (recompute a canonical digest on the
  receiving side). `tar` + `zstd` is not canonical — ordering, mtimes, uid/gid,
  xattrs, compression level all vary — so this needs an `mtree`/NAR-style
  normaliser, a much larger project than carrying the original file.

**The integrity of a repacked bundle can only ever rest on the transfer medium.**
That is stated plainly in `docs/DATA_INTEGRITY.md` rather than dressed up.

### 2. The bundle carries the signed upstream artefact

`export_offline_bundle` downloads the upstream tarball **and** its `.minisig`
and writes both verbatim. It runs on a connected machine by definition — that is
the workflow, and the CLI has always said so.

The isolated machine then runs the *identical* verification path as the network
fetch. The special case disappears rather than acquiring a weaker parallel one.

`repack_cache_unverified` retains the old behaviour for offline-to-offline
mirroring, under a name that cannot be mistaken for a verified export. `--from`
refuses its output.

### 3. Refuse, never warn

An unsigned bundle is refused. A stripped signature and a release predating
signing are indistinguishable from the client, and the operations review was
blunt about what warnings become on an isolated network: *"hit enter"* within a
week.

There is **no bypass flag**. From #594: an escape hatch is the first thing a
frustrated user pastes from a forum thread. `install_tarball_unverified` is
`#[cfg(test)]`-gated, so it cannot exist in a shipped binary at all.

### 4. The version gate is mandatory, and it is the rollback defence

`install_tarball_atomic` writes to `v{DATA_VERSION}` unconditionally, so a
validly-signed *foreign-version* bundle would populate the wrong directory.

More importantly: **a signature alone does not stop rollback.** An old,
legitimately-signed release verifies perfectly. Two reviewers flagged this
independently. Binding the install to the version this build pins is what stops
it — which is also why the SHA-256 pin from #577 stays alongside the signature
rather than being replaced by it.

A signature whose trusted comment omits `tag=` is **refused**, not waved
through: a gate that quietly stops applying to signatures lacking a field is a
gate an attacker simply omits the field to bypass.

### 5. Verify and extract the same inode

The install opens the archive once, verifies, rewinds, and extracts from the
same descriptor. Re-opening by path in between left a window where an attacker
with write access to the media could swap the file after it passed verification
— the flock serialises HYRR against itself, not against them.

### 6. Re-derive the pinned signing key at build time

This came from outside the issue's scope and is the highest-leverage change in
it. The adversarial review ranked as its top attack: **a pull request that
quietly edits `data_signing_pubkey`.** One merge swaps the trust root for every
user, permanently — and every signature check then *passes*, because it is
checking against the attacker's key.

Verifying signatures against a key nobody re-derives is a closed loop.
`core/build.rs` now re-derives it from the pinned submodule's published
`docs/security/data-signing-key.pub` and fails the build on drift, mirroring the
existing `data_version` guard. Editing the key alone breaks the build; editing
key *and* submodule together is two obviously-related changes in one diff, which
is what review is for.

## Consequences

- The air-gapped path has the same trust root as the network path. This was the
  last unauthenticated route into the cache.
- `--offline-bundle` now requires network on the exporting machine. That
  machine is connected by definition, so this is not a regression — but the
  install docs had to change, since users copy **two** files now.
- A cache installed before this reads as *complete but not verified*
  (`.verified` sidecar, `cache_status()`). Reads are deliberately **not** gated
  on it: gating bricks every existing offline install at upgrade, which is what
  pushes operators to `cp -r` across a diode with no verification at all.

## Known limitations, recorded not hidden

**Content-scanning (CDR) gateways.** OPSWAT MetaDefender, Deep CDR and similar
are standard at hospitals and Tier-1 nuclear sites. They open an archive in
transit, scan each entry and **repack** it: data intact, signature dead — at
exactly the sites with the strongest verification requirements. The operations
review put this at roughly 20% of realistic deployments.

The fix is upstream and filed as
[exoma-ch/nucl-parquet#296](https://github.com/exoma-ch/nucl-parquet/issues/296):
publish a **signed content manifest** (per-file digests, Debian `Release` model)
alongside the archive signature, so verification survives a repack. Notably the
cryptographic review arrived at the same mechanism from an unrelated direction —
subsetting, so a user who needs one library need not move 785 MB across a diode.
Two independent motivations converging on one mechanism is why it is the
recommended upstream shape.

**Nothing re-hashes an installed tree.** Upstream signs the archive, not its
contents, so after extraction there is nothing authenticated left to compare a
file against. `cache_status()` reports provenance and says so, rather than
walking the tree and comparing it to nothing — which would repeat the exact
"reads as a control, isn't one" failure this ADR rejects. Also unblocked by #296.
